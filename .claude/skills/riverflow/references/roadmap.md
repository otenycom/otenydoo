- [ ] **Make the Add Service picker usable for Operations** *(Fred + Ries, Sep 2026)*. Adding an ad-hoc service to a log entry currently offers about 30 templates in one flat list, and the list will keep growing as credential services are built. The placement guard rails (see [SKILL.md § Template Placement Guard Rails](../SKILL.md#template-placement-guard-rails)) already cut the catalog by subject; they do not make what remains scannable. Four measures were agreed, in order of value:
  - **A quick-list flag on the template** — a boolean, rendered as a short header strip of the handful of templates that are genuinely picked by hand (doctor appointment, and similar). Ries has built this shape before and rates it the single biggest win.
  - **Leave out what is always auto-added.** Templates that an auto-add rule creates in every relevant case (sign-off confirmations and the like) never need to be chosen manually. They occupy most of the list and belong behind a "show the rest" control.
  - **Name by group, so the list sorts meaningfully.** Fred's proposal: start the service name with the group it belongs to. Everything doctor-related begins with the same word, so alphabetical order becomes useful order. Search already finds a template whose keyword sits mid-name; the gap is recognising the right one **at a glance**.
  - **Allowed subject *workflows*, not only subject models.** `allowed_subject_model_ids` restricts a template to log entry / employee / ship. Restricting to the subject's **workflow** would narrow the picker further — e.g. templates that only make sense on a sick-leave entry. Named "allowed subject workflows" to match the existing `subject` vocabulary, deliberately not "parent", since a service need not have a parent.

  **The motivating case, and the caveat.** Operations kept a sick crew member's hospital appointments on a whiteboard and in the old calendar rather than adding a doctor service, because the picker meant nothing to him — yet with someone sitting beside him he did it correctly. Ries's reading is that this is **as much a training gap as a UI gap**: ordinary Odoo implementations teach the buttons instead of building custom UI, and Crewradar has done almost no training. The fix is therefore the list **plus** a few rehearsed exercises, not a one-click shortcut. The meeting record this item came out of is kept in the consuming business's own skill bundle.

## Completed

- [x] Bot execute door: a bot lists the same `transition_buttons_json` a person sees, opens `prepare_transition_action` (public `/json/2/` name), then `oteny.form.session` `open` on that dict. `bot_claim` is open-and-save. It runs `action_save`. It does not write `state_id` raw. `set_deadline_relative` writes the two relative fields and drops the email-sender `today + 1`. The human fence admits `riverflow_bot_caller`. Tests: `test_bot_execute.py` plus the relative case in `test_transition_email_template.py`. Version 19.0.1.1237. The recipe the bot reads is the module Talent `riverflow/talents/riverflow-execute-talent/` (git path). Operator `.claude` pages point at that bundle. Proven live on a pilot bot, documented as a worked example in a consuming business's own skill bundle.
- [x] Host Talent layout: `oteny_bot/talents/oteny-odoo-access-talent/` and `riverflow/talents/riverflow-execute-talent/`. Delivery is the same git-path shape as a client Talent. No Odoo download API. No `terminal` requirement. See [Oteny Bots — Host Talent delivery](../../oteny-bot/SKILL.md#host-talent-delivery).
- [x] One live slot (derived): `riverflow.state.bot_login_hold` + `_bot_one_live_slot_defers` / `_bot_drain_peers` on the bot mixin. Why: a bot that shares one browser and one login must not run two isolated turns at once. Drain is primary (inline in the occupant's `write`). A queued sibling wins. If none waits, drain resumes one fresh SLA-less login park (`_bot_resume_login_park`). The 3-min cron is the belt for queue. Mid-turn is not adoptable. Strict at dispatch; relaxed at consume (`_bot_claim_is_live`); exclude-self admits a parked login's own resume. A SLA-less park does not occupy. No occupancy fields on `oteny.bot`. Helpers `_bot_one_live_slot_occupant_of_workflow` / `_bot_one_live_slot_queued_of_workflow` feed the Oteny Bots Slot UI. `bot_token_check` accepts `work_token` alone (`res_id` optional). HR never sees `bot_role` claim/work; a live claim shows the working note plus only that state's `is_bot_timeout` abort (19.0.1.1257); bot queue/fill uses `no_primary`. D238 lock mechanics stand. Which states set the flag stays in the owning app's workflow XML. Tests: `test_bot_one_live_slot.py`, `test_transition_buttons_bot_hide.py`. Version 19.0.1.1218.

Icons now show the ACTION that completes the task (see [SKILL.md § Choosing the Workflow Icon](../SKILL.md#choosing-the-workflow-icon)). Pushed to existing databases by post-migrations guarded on the shipped value so manual overrides survive (riverflow 19.0.1.1198, crewradar 19.0.9.174, crewradar_cuneus_sign 19.0.5.53/19.0.5.54). Same riverflow migration retired the never-live "To Be Invoiced" workflow stub (XML file removed; noupdate rows deleted states-first, guarded on zero service usage) and archived the hand-made "AB Appointment (Do not use, work in progress)" workflow. New guard test `riverflow/tests/test_workflow_icons.py` (post_install) validates every workflow/transition/transition-action icon against the FA 4.7 CSS shipped with the web module, making the empty-box bug class structurally impossible to reintroduce.
- [x] Template placement guard rails: Three fields on `riverflow.service` templates (`can_be_root_service`, `can_be_child_service`, `allowed_subject_model_ids`) prevent users from instantiating templates on wrong subjects (e.g. log-entry-only templates on employees/ships) or in wrong roles (root vs child). Central validation in `_check_template_placement()` called from `_create_service_member_from_template`. Shared helper `_template_placement_allowed()` used by both server-side check and wizard filtering in `_add_template_start_transitions`. Bypass via `skip_service_template_placement_check` context flag. 42 of 44 root templates restricted to `crewradar.log.entry`, 1 to `hr.employee`, 1 unrestricted. 10 tests in `test_service_template_placement.py`. Post-migrate scripts for live databases (noupdate XML). Version 19.0.1.1105.
- [x] Dynamic wizard Selection fields: Wizard `use_project_deadline_from` now uses a dynamic selection function (`_selection_use_project_deadline_from`) that reads from `riverflow.service` at runtime, instead of a hardcoded list. Fixes `ValueError` crash when opening the transition wizard on services with `root_appointment` or `creation` deadline mode (~160 production services). Inheriting modules no longer need `selection_add` on the wizard. Also fixed `default=list` on the Json whitelist field and re-enabled the `filterable_selection` widget. 3 tests in `riverflow/tests/test_wizard_selection_sync.py`.
- [x] Send Notification workflow (`workflow_service_send_notification`): variant of Send Email where the primary "Send" transition goes directly to Done (fast path for one-shot notification emails). Same 4 states as Send Email; secondary "Send and Await Reply" transition available for flexibility. First consumer: A1 deferred child services (Send A1 to Client, Send A1 to Employee). Defined in `riverflow/data/service_send_notification_workflow.xml`.
- [x] Incomplete children warning on service wizard: when the user manually transitions a service whose state has `auto_progress_on_children_done = True`, the wizard shows an `alert-warning` banner listing incomplete child services **only if the chosen transition targets a non-cancelled end state** (`is_end_state` and not `is_cancelled_state`). **Back** (non-end target) and **Cancel** (cancelled end) do not show the warning; circumvent transitions to a normal end state (e.g., A1 "Sent already" → Done) still do. A confirmation checkbox ("I confirm — skip the child services") allows override; `action_save()` raises `UserError` if the warning is set and the checkbox is unchecked. Tests: `riverflow/tests/test_auto_progress.py` (four cases) and `crewradar_cuneus_sign/tests/test_a1_workflow.py` (Back from Send Issued A1 with pending children).
- [x] Auto-progress on children done: `auto_progress_on_children_done` Boolean flag on `riverflow.state`. When set, services in this state auto-progress to the next sequential workflow state once all active child services reach an end state. Implemented via `_check_parent_auto_progress()` and `_auto_progress_to_next_state()` on `riverflow.service`, hooked into the transition wizard's `action_save()` after `create_related_records()`. Combines with `create_on_state_id` deferred children for fan-out/fan-in patterns. First consumer: A1 workflow "Send Issued A1" state spawns two email-sending children and auto-completes to Done. 7 generic tests in `riverflow/tests/test_auto_progress.py`.
- [x] Transition action_context deadline overrides: `clear_deadline` and `set_deadline_to_today` context keys handled in `action_save` of the base transition wizard. Allows per-transition deadline manipulation without custom wizard subclasses. Used by A1 workflow: Await Reply transitions clear deadline (SVB response time unpredictable), Done transitions freeze deadline to today (completion date).
- [x] Weekend deadline rule: `weekend_deadline_rule` selection field on `riverflow.service` that shifts computed deadlines off weekends to the preceding Friday (`friday_before`) or following Monday (`monday_after`). Only applies to computed deadlines (`is_days_relative_to_project_applicable = True`); manual dates stay as-is. Migration sets rule on all existing services using structural heuristic (offset <= 0 -> friday, > 0 -> monday). Added in version 19.0.1.1025.
